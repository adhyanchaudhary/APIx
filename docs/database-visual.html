Idempotency: write_index() deletes the existing rows for a given (index_date, lead_window_days) before inserting, so re-running a day replaces rather than duplicates.

Step-by-Step: How a Daily Index Row Is Computed

→ Step 1 — Collapse cleaned rows to the minimum fare per (route, lead_window_days, scrape_date). Rows with is_outlier = 1 are excluded.

→ Step 2 — Within each window, the first date with data becomes the base period: P₀ per route.

→ Step 3 — For each later day, compute the route index and the weighted aggregate:

route_indexi(t) = Pi(t) / Pi(0) × 100
aggregate_index(t) = Σi route_indexi(t) × wi

In the real code, the aggregate is summed over all available routes; missing routes contribute 0 and weights are never re-normalised.

Rolling Views

Weekly and monthly indices are simply moving means of the daily route_price, route_index, and aggregate_index, computed per window with window=7 and window=30 respectively, and min_periods=1 so early days still produce a value.

  • run_index.py reads cleaned_flights → computes daily → rolls to weekly/monthly → writes all three tables.
  • All math lives in src/indexer/api_index.py (204 lines); the CLI wrapper is src/indexer/run_index.py (80 lines).
Key takeaway: one SQLite file → one progression. raw → cleaned → daily → weekly → monthly. The base day is always 100, and the weights in config/indexer.yaml decide exactly how much each route moves the aggregate.
