1. The Problem — Why This Matters

The Indian government tracks inflation through the Consumer Price Index (CPI). One component of CPI is airfare inflation — how much flight ticket prices change over time. Today, this is measured by manually collecting prices from a handful of ticketing counters.

That's a broken process. Here's why:

Prices Swing 200–400% in a Day

Airlines use dynamic pricing. A Delhi–Mumbai ticket can jump from ₹3,000 to ₹12,000 within hours based on demand, time, and seat availability. Manual collection can never capture this volatility.

90%+ Fares Are Sold Online

Yet the government still collects data from physical counters. The data is outdated, unrepresentative, and misses the online-only deals, OTA coupons, and surge pricing that real passengers pay.

RBI Needs Real-Time Data

The Reserve Bank of India uses airfare data to set monetary policy. Getting delayed or inaccurate price signals can lead to poor economic decisions that affect 1.4 billion people.

No Route-Level Visibility

Current CPI gives a single national average. It doesn't tell you if Delhi–Bengaluru got expensive while Mumbai–Chennai got cheaper. Policymakers need that granularity.

2. The Solution — What We're Building

We're building APIx (Airfare Price Index) — an automated pipeline that scrapes real-time flight prices from Google Flights every day, cleans the data, computes a weighted price index, and presents it on a dashboard.

"Doesn't an airfare index already exist?" — The honest answer

Fair question. Here's what exists vs. what doesn't.

  • Airline fare-trackers and commercial products DO exist (Google flight trends, Farecast-style tools, academic indices). So the idea of tracking fares isn't new.
  • But India's official statistical office (MoSPI) has no automated index. Its airfare CPI is still collected manually from a handful of physical ticketing counters — days late, and unrepresentative, because 90%+ of fares are now sold online.
  • This project isn't inventing a new statistic. It uses the same trusted Laspeyres/CPI method the government already uses, but applies it to live, automated, route-level data it currently can't get.

So the unique value isn't "an index." It's the reproducible, automated pipeline — scrape → clean → index → dashboard, run daily — that gives NSO and RBI accurate, high-frequency, DGCA-weighted airfare inflation data for the first time. That institutional tool doesn't exist today.

5. The Index Formula — How APIx Is Calculated

We use a Laspeyres-style weighted basket index — the exact same method India already uses to build its Consumer Price Index (CPI). So instead of reinventing the wheel, we apply the official, internationally standard technique to airfares. Here's what that means, step by step.

First, a simple analogy to "get it"

Imagine you want to track how much a grocery basket costs. You don't track every product in the shop — you pick a fixed basket (e.g. 1kg rice + 1L milk + 5 eggs), record the total cost today, record it again every week, and see how the total moves up or down over time.

APIx does exactly this, but for airplane tickets. Our "basket" is the set of 12 flight routes (DEL–BOM, DEL–BLR, etc.). Each route is like an "item" in the basket. We record the average ticket price for each route, then compare today's prices to a fixed starting point ("base period") and turn the change into a single easy-to-read number called the index.

The 6 steps to computing APIx

Every day, we scrape fares for each route

The scraper collects the lowest available fare for all 12 routes at 3 booking windows (T+1, T+7, T+30). After cleaning, for each route we compute that day's average fare. This is the day's "price" for each item in our basket.

We fix a "base period"

The very first day we have enough good data becomes the base period. We set that day's index = 100 (a convention in statistics). All future days are compared against this baseline. Our config requires a minimum of 30 data points before we trust the base value.

Compute each route's index (the "item" change)

For every route, we ask: "how much has this route's price changed vs the base day, in %?"

Route Index = (Today's Avg Fare ÷ Base Day Avg Fare) × 100

If DEL–BOM averaged ₹4,000 on the base day and costs ₹5,000 today, its route index = 125 (meaning prices went up 25%).

Weight each route by how popular it is

Not all routes matter equally — Delhi–Mumbai carries more passengers than Chennai–Bengaluru. We weight each route by its DGCA passenger-traffic share. Cities are assigned weights: DEL 30%, BOM 25%, BLR 25%, MAA 20%. So bigger routes pull the overall number more. This is what makes it "weighted." A route with a 15% weight contributes 15% of the answer; a route with 3% contributes only 3%.

Combine the routes into one aggregate APIx

The final APIx is a weighted average of all the route indices:

APIx = (Route1 Index × Wgt1) + (Route2 Index × Wgt2) + ... + (Route12 Index × Wgt12)

Every route "votes" with a weight, and the final number is the traffic-weighted total. On the base day, this equals 100. Every day after, it tells you the overall change in airfare inflation, regardless of which specific routes moved.

Store at 3 frequencies

We compute and store the index at daily, weekly, and monthly frequency in three separate SQLite tables (daily_index, weekly_index, monthly_index). The value is rounded to 2 decimal places. RBI and NSO can then pull whichever frequency they need.

Concrete worked example (simplified to 3 routes for clarity)

Say our "basket" has just 3 routes. On Day 1 (the base day), we record their average fares. We assign each route a weight based on passenger traffic:

Route Weight Day 1 Avg Fare (Base) Day 30 Avg Fare
Delhi ↔ Mumbai35%₹4,000₹5,000
Delhi ↔ Bengaluru40%₹4,500₹4,500
Mumbai ↔ Chennai25%₹3,000₹3,300

Delhi ↔ Mumbai(5000 ÷ 4000) × 100125

Delhi ↔ Mumbai0.351250.35 × 125 = 43.75

APIx (Day 30)
43.75 + 40.00 + 27.50 = 111.25

Since Day 1 = 100, an APIx of 111.25 means the overall basket of airfares rose 11.25% over 30 days. The exact contribution of each route: Mumbai–Chennai rose 10%, but because it has a small weight (25%) it pulled the total up less than Delhi–Mumbai (35% weight) rising 25%. This is why weighting matters.

Why this particular method?

  • It's the official standard. Same Laspeyres approach as CPI — policymakers already trust it.
  • It isolates pure price change. Because the basket is fixed, a rise in APIx means prices rose, not that people bought more expensive routes.
  • It's comparable. RBI can read "airfare index 111.25" the same way they read "CPI 118" — a consistent, comparable scale.
  • Transparent. If a route has no data on a given day, we skip it rather than guess (no imputation).

Still not sure? Key one-liner

APIx answers one simple question: "Compared to our starting day, how much more (or less) does the same basket of 12 flight routes cost now?" Base day = 100, and every number above or below 100 is a percentage change from then.

8. Detailed Component Breakdown

Scraper Module — src/scraper/
  • base.py — Abstract BaseScraper class that defines the contract all scrapers must follow
  • driver.py — Async Playwright browser context manager. Handles Chromium launch, viewport size, user-agent rotation, and timeouts
  • google_flights.py — The actual scraper (314 lines). Builds Google Flights search URLs, navigates to results, parses aria-label attributes on flight cards (more stable than CSS selectors), extracts price, carrier, times, duration, stops via regex
  • run_scrape.py — CLI entry point. Iterates all 12 routes × 3 windows = 36 tasks, applies rate limiting (max 60 req/hr), exponential backoff retry (3 attempts), saves validated FlightRecord objects to SQLite
Cleaner Module — src/cleaner/
  • clean.py — Pandas-based pipeline (133 lines)
    • Computes MD5 dedup hash per record (route + carrier + time + fare + window)
    • Removes duplicate entries
    • Handles null fares (configurable: drop or forward-fill)
    • IQR-based outlier detection grouped by route + lead window
    • Quality scoring (0.0–1.0) based on field completeness
    • Writes results to cleaned_flights table
Data Models — src/models/schemas.py
  • FlightRecord — 16-field Pydantic model: origin, destination, carrier, flight_no, departure_time, arrival_time, duration_mins, stops, base_fare, taxes, total_fare, currency, lead_window_days, scrape_date, scrape_timestamp, quality_score
  • RouteConfig — origin/dest pair with DGCA weight
  • CityConfig — city code, name, traffic weight
  • IndexEntry — index_date, route, weight, route_price, route_index, aggregate_index, base_period
Database — src/storage/database.py
  • SQLite single-file database at data/apix.db
  • 5 tables: raw_flights, cleaned_flights, daily_index, weekly_index, monthly_index
  • init_db() creates tables on demand, get_connection() returns live connections
  • Currently holds: 356 raw flights, 75 cleaned flights
Index Builder — src/indexer/ (PLANNED)
  • Reads from cleaned_flights
  • Computes per-route average fare for each day
  • Calculates route-level index: (today_avg / base_avg) × 100
  • Aggregates into overall APIx using DGCA traffic weights
  • Produces daily, weekly, and monthly index values
  • Requires minimum 30 data points before computing index
  • Skips missing routes (no imputation) for transparency
Dashboard — src/dashboard/ (PLANNED)
  • Streamlit web app reading from SQLite
  • Live daily APIx display
  • Price trend line charts by route
  • Sector-wise heatmap (city-pair matrix)
  • Lead-time elasticity curve (price vs booking window)
  • Carrier-wise comparison charts
  • Raw-data explorer with filters
  • Target: <5s cold load, <1s cached chart render
Scheduler — (PLANNED)
  • APScheduler-based daily job runner
  • Triggers full pipeline: scrape → clean → index → dashboard refresh
  • Logging and error handling for each stage
  • Designed to run as a local scheduled task (not a long-running daemon for MVP)

9. Key Constraints

Technical Constraints
  • Python 3.10+ required (running 3.13)
  • Headless Chromium only — no GUI browser dependency
  • SQLite as sole database — zero infrastructure
  • Max 1 concurrent scraper — avoid anti-bot triggers
  • Max 60 requests/hour — respectful rate limiting
  • No secrets in code — use .env + python-dotenv
  • Windows-compatible development
Data Constraints
  • Google Flights only for MVP
  • Max 4 cities, 12 routes, 3 lead windows
  • Fares in INR only
  • Minimum 30 data points before computing index
  • Scraping frequency: once daily (batch, not real-time)
  • Historical data: max 90 days
Ethical / Legal Constraints
  • Honor robots.txt at all times
  • No scraping login-gated content
  • Respect Google Flights Terms of Service
  • Minimum volume, maximum value — fewest queries for valid index
  • Cache aggressively to reduce repeat requests
  • No personal data collected — no PII, no tracking

10. Risks & How We Handle Them

Anti-Bot / CAPTCHA

We use rate limiting (60 req/hr), human-like random delays (3–8s), exponential backoff retry, and session management to stay under detection thresholds.

Google Flights Layout Changes

We parse aria-label attributes (structured text) instead of fragile CSS selectors. The scraper module is isolated — easy to swap to OTAs if needed.

Terms of Service

Ethical scraping policy: robots.txt compliance, modest volumes, cache-first approach, source attribution in documentation.

Data Inconsistency

Robust cleaning pipeline with IQR outlier detection, null handling (drop/forward-fill), deduplication, and quality scoring.
