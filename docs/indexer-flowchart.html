APIx Indexer — Deep Dive

Zoomed into Phase 3: from apix.db cleaned flights to the daily / weekly / monthly APIx indices — every function, its inputs, and the math behind the 36-cell basket.

Orchestrator — what run_index does, in order

Inputs it loads
  • cleaned_flights table (all rows)
  • indexer.yaml → 12 route weights (normalised to 1.0)
  • window_weights → 1:0.20, 7:0.30, 30:0.50
  • active_windows → [1, 7, 30]
  • estimator config (names + trim fractions, price method)
  • round_to → 2 decimal places
Pipeline ordering (in run_index)
  • 1. read cleaned flights — early-return zero counts if empty
  • 2. load weights, windows, estimator config
  • 3. collapse fares → route_price_per_day
  • 4. keep only active windows
  • 5. daily composite → compute_daily_index
  • 6. 7-day → compute_rolling_index
  • 7. 30-day → compute_rolling_index
  • 8. write the three index tables
Entry points
python -m src.indexer.run_index [--db path]

3 log.info banners: weights + windows, route-price method, estimators. Returns {daily, weekly, monthly} row counts.

1

Collapse fares into cells — api_index.route_price_per_day()

Cell = (route × lead window × date)
  • Group raw cleaned rows by (route, lead_window_days, scrape_date)
  • Collapse the fares in a cell to one price using method (default median, or min)
  • Rows with is_outlier = 1 are excluded from the price (they stay in the DB)
  • Null total_fare rows are dropped first
Carry-forward (_carry_forward_missing_dates)
  • Fills every calendar day between a group's first and last observed date
  • Gap days inherit the last known fare (forward-fill)
  • Dates before the first observation stay missing (nothing to carry from)
Why? a coverage gap no longer drags the aggregate down for no economic reason — the route is simply "still at yesterday's price".
2

The daily composite — api_index.compute_daily_index()

Build the 36-cell basket
  • cell_weight = route weight × window share, for all 12 routes × 3 windows
  • If no window_weights given, active windows share equal weight
base_date = first date with ANY data base = each cell's fare on base_date (index = 100 on day one) first_price / first_date = a cell's OWN first observation (fallback for cells absent on the shared base date)
Score every present cell
  • Base price = fare on the shared base date if the cell existed then
  • Otherwise use the cell's own first fare and join the basket at 100 on its start date
  • Non-positive base fares are skipped (division guard)
route_index(cell) = today_price / base_price × 100 weight(cell) = route_weight(cell) × window_share(cell)
One headline per date
  • The composite = aggregate(route_indices, cell_weights, estimator, trim_frac) over the cells present that day
  • Aggregate is stamped identically onto every row of that date
Key fact: there is ONE composite number per date (not one per window). Weights re-balance over the cells present each day, so a late-starting window expands the basket without jerking the headline.

Inside the headline — estimators.aggregate() & the estimator registry

aggregate(values, weights, estimator="weighted_mean", trim_frac=0.10) dispatches by name to one of three estimators. Trimmed mean needs the trim fraction; everything else just calls the registry.

weighted_mean — classic Laspeyres
Σ(v × w) / Σw

Each route index weighted by its basket share. Plain weighted average — kept as a selectable option, not the active default.

weighted_trimmed_mean — configured default (CPI-style)
sort by value → clip each element's weight so cumulative weight stays in [trim·Σw, (1-trim)·Σw] → re-balance & average the survivors
  • Trimming is measured in weight mass, not route count — a small route is fully eaten, a big route only shaved
  • If nothing survives (trim ≥ 0.5) it falls back to the weighted median
weighted_median
sort by value → the value where cumulative weight crosses 0.5·Σw

Splits an exact half boundary by averaging the two neighbours.

DEFAULT_TRIM_FRAC = 0.10 ESTIMATORS = {"weighted_mean", "weighted_trimmed_mean", "weighted_median"} chosen in config/indexer.yaml → aggregation_estimator

3

Weekly & monthly rollups — api_index.compute_rolling_index()

Rolling smoother (_rolling_agg)
  • Applied per (window, route) for route_price and route_index
  • Applied per window only for the composite (one number per date)
  • min_periods=1 → early days still yield a value
mean median trimmed_mean (rolling_trim_frac = 0.10)
Two calls
  • window_days = 7 → weekly
  • window_days = 30 → monthly
  • Output keeps the canonical INDEX_COLUMNS schema, rolled values rounded
4

Persist — api_index.write_index()

Idempotent upsert
  • Rejects any table name outside INDEX_TABLES
  • For each (index_date, lead_window_days) group: DELETE existing rows, then bulk-insert
  • Re-running for the same date re-computes instead of duplicating
  • Returns the number of rows written

Research tools that consume the same inputs

Synthetic data
synthetic.py → make_synthetic_cleaned()

Seeded, cleaned-flights-shaped generator (price drift, weekend bumps, spikes, deliberate gaps) so the research below is reproducible before real 30-day data lands.

Stability metrics
metrics.py
  • stability_stats() — mean/stdev/max day-to-day headline move + extreme-day count
  • aggregate_by_day() — the unique daily composite series for a window
  • compare_aggregation_estimators() — estimator × window stability table
  • route_sensitivity() — headline move if a route loses all data (SMALLER = better)
  • weight_elasticity() — headline move per +0.01 route weight (which DGCA weights matter)
  • best_estimator_per_window() — calmest estimator per window
Report
report.py → run_report()
  • Uses real db by default; falls back to synthetic when <3 routes or <5 dates
  • Prints: aggregation comparison, 7-day rolling comparison, route sensitivity + weight leverage
