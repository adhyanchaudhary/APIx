Phase 1 Explained — The Scraper

Playwright + Google Flights: from a URL to validated FlightRecords in the database
← Phase 0 Walkthrough: base.py →

Purpose

Phase 1 turns Google Flights into a disciplined data source. For each of 12 routes × 3 lead windows it fetches live flights, validates them into FlightRecord models, rate-limits politely, retries transient failures, and stores everything in raw_flights.

1. base.py — The Contract (15 lines)

src/scraper/base.py
Hint, not implementation.
class BaseScraper(ABC):
    @abstractmethod
    async def fetch_flights(
        self, origin, dest, travel_date, lead_window_days
    ) -> list[FlightRecord]:
        ...

BaseScraper guarantees every scraper exposes one async method, fetch_flights, which returns validated FlightRecords. This is what lets run_scrape.py stay source-agnostic — swap Google for another engine by supplying a new subclass.

2. driver.py — Safe Browser Lifecycle (47 lines)

src/scraper/driver.py
Launch → use → always close.
async with create_browser_context() as context:
    page = await context.new_page()
    await page.goto(...)   # work happens here
  • load_scraper_config() reads config/scraper.yaml.
  • create_browser_context() is an @asynccontextmanager: it launches Chromium with the configured viewport (1280×900) and user agent, sets the default timeout, then always closes the context and browser in a finally — no leaked processes.
  • Playwright itself auto-cleans the driver process.

3. google_flights.py — The Core (314 lines)

src/scraper/google_flights.py (314 lines)
Where all the real DOM work happens.

The pipeline inside one call

  • 1Build URL — encode origin, destination, travel date, and lead window into the Google Flights search URL.
  • 2Wait for results — wait for the flight results container to render (element_wait_timeout: 15s).
  • 3Collect aria-labels — run page.evaluate() inside the browser to grab every flight card's aria-label. Google Flights encodes time, airline, and fare text in these labels, which is far more reliable than scraping styled DOM.
  • 4Parse each label — a regex-based extractor splits each label into departure time, arrival time, duration, stops, carrier, and fare — feeding a FlightRecord.
  • 5Rate limit + retry — sleep a random 3–8s (from config) between requests; retry up to 3 times with ×2 backoff (3s → 6s → 12s) on transient failures.
Why aria-label? Google's dynamic UI rearranges styled elements constantly; the accessibility label is a stable, machine-readable transcript of each flight's data.

4. run_scrape.py — The Batch Orchestrator (118 lines)

src/scraper/run_scrape.py (118 lines)
for route in routes:                 # 12 directional routes
    for lead in lead_windows:        # 1, 7, 30
        travel = today + timedelta(days=lead)
        records = await scraper.fetch_flights(origin, dest, travel, lead)
        _insert_records(records, scrape_date_str)   # -> raw_flights
  • Reads the route basket and windows from config/routes.yaml, and rate/retry settings from config/scraper.yaml.
  • Tracks total_inserted and total_failed per route×window; logs a clean run summary.
  • _insert_records() persists batches into raw_flights using the storage layer.
  • ASGI-style async entry point: python -m src.scraper.run_scrape.

Heads-up: smoke tests and the batch runner hit the live web. Always operate within the configured rate limit (60 req/hour) and never run them through CI.
Key takeaway: the scraper is a polite, retrying, schema-validating bridge between Google Flights and raw_flights. Its output feeds directly into Phase 2 (cleaning).
