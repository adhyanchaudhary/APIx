What We Created — File by File

1 .env — The Robot's Settings File

📄 .env
A private settings file that stores configuration the robot needs but shouldn't be shared publicly.

This file holds things like:

  • Where to find the browser — Playwright needs to know where Chromium (the browser) is installed
  • How much to log — LOG_LEVEL=INFO means "tell me what's happening, but don't be too verbose"
  • Speed limits — max 60 requests/hour, wait 3–8 seconds between each request (so Google doesn't block us)
This is like the settings screen on your phone — volume, brightness, wallpaper. The robot reads these every time it starts.
# From our actual .env file:
LOG_LEVEL=INFO
MAX_REQUESTS_PER_HOUR=60
REQUEST_DELAY_MIN=3
REQUEST_DELAY_MAX=8

2 .gitignore — The "Don't Share This" List

📄 .gitignore
A list of files that should NOT be uploaded to GitHub when you share your code.

Some files contain secrets (like .env) or generated data (like the database data/apix.db). You don't want to accidentally upload these to the internet.

Think of it as a packing list for a trip — but instead of listing what TO bring, it lists what to LEAVE at home.
# From our actual .gitignore:
.env          ← secrets, don't share
data/*.db     ← generated data, re-create anytime
__pycache__/  ← Python's scratch files, not needed

3 requirements.txt — The Shopping List

📄 requirements.txt
A list of all the external tools (libraries) our project needs to run.

Python doesn't come with everything built-in. We need to install extra tools. This file tells Python exactly which tools and which versions to download.

Like a recipe's ingredient list — before cooking, you check you have flour, sugar, eggs. Before coding, we check we have all the libraries.
# From our actual requirements.txt:
playwright>=1.40.0   ← browser automation tool
pandas>=2.1.0        ← data cleaning tool (like Excel for Python)
numpy>=1.26.0        ← math calculations
pydantic>=2.5.0      ← data validation (like a strict form-filler)
streamlit>=1.29.0    ← web dashboard builder
pytest>=7.4.0        ← testing tool

Running pip install -r requirements.txt downloads and installs all of these automatically.

4 config/routes.yaml — The Route Map

📄 config/routes.yaml
Defines which cities and flight routes the robot should check prices for.

This file answers three questions:

  1. Which cities? — Delhi, Mumbai, Bengaluru, Chennai
  2. Which routes? — 12 directional routes (Delhi→Mumbai, Mumbai→Delhi, etc.)
  3. How far ahead? — Check prices for flights leaving in 1 day, 7 days, and 30 days
Like a delivery company's route sheet — "Today we need to check prices on these 12 routes, for 3 different booking windows."
# From our actual routes.yaml:
cities:
  DEL: { name: "New Delhi",  weight: 0.30 }  ← 30% of all Indian air traffic
  BOM: { name: "Mumbai",     weight: 0.25 }  ← 25%
  BLR: { name: "Bengaluru",  weight: 0.25 }  ← 25%
  MAA: { name: "Chennai",    weight: 0.20 }  ← 20%

lead_windows: [1, 7, 30]  ← check 1-day, 7-day, 30-day ahead fares

5 src/models/schemas.py — The Form Template

📄 src/models/schemas.py
Defines the exact shape of data we expect to collect — like a blank form that must be filled out completely.

When the robot scrapes Google Flights, it gets raw, messy data. This file defines what a valid flight record looks like. If data doesn't match this template, it gets rejected.

Like a job application form — you MUST fill in your name, email, phone. If you leave any field blank, the form is rejected. Our schema does the same for flight data.
# What one flight record looks like (simplified):
{
  "route": "DEL-BOM",          ← which route
  "carrier": "IndiGo",         ← airline name
  "flight_no": "6E-201",       ← flight number
  "base_fare": 4500.00,        ← ticket price without taxes
  "taxes": 850.00,             ← government taxes
  "total_fare": 5350.00,       ← what you actually pay
  "lead_window_days": 7        ← checking 7 days ahead
}

The schema enforces rules: total_fare must be positive, origin must be exactly 3 characters, etc.

6 src/storage/database.py — The Notebook

📄 src/storage/database.py
Creates and manages the SQLite database — a structured file where all flight data is stored.

A database is just a structured file that stores data in tables (like Excel spreadsheets). SQLite is the simplest kind — it's just a single .db file, no server needed.

Our database has 5 tables:

Table NameWhat It Stores
raw_flightsMessy data straight from Google Flights (untouched)
cleaned_flightsData after removing errors, duplicates, and outliers
daily_indexThe APIx number calculated every day
weekly_index7-day rolling average of the index
monthly_index30-day rolling average of the index
Think of it as 5 different notebooks: one for raw notes, one for cleaned notes, and three for calculated results (daily, weekly, monthly).
# Creating the database:
python -c "from src.storage.database import init_db; init_db()"

# Output:
# Database created at: C:\Users\LENOVO\Desktop\SIH-2026\data\apix.db

7 config/scraper.yaml — The Robot's Behavior Rules

📄 config/scraper.yaml
Controls how fast the robot works, how it handles errors, and what browser settings to use.

Key settings:

  • Rate limiting: Max 60 requests/hour, wait 3–8 seconds between requests
  • Retries: If a page fails to load, try 3 times with increasing wait times (3s, 6s, 12s)
  • Browser: Headless (invisible) Chromium, 1280×900 window
If we send too many requests too fast, Google will block us. The rate limits are there to keep us under the radar.

8 config/indexer.yaml — The Calculator Settings

📄 config/indexer.yaml
Controls how the airfare index number is calculated and how to detect bad data.
  • Base period: First available day = index value 100
  • Outlier detection: Use IQR method (removes prices that are way too high or too low)
  • Minimum data: Need at least 30 days before the index is considered valid

9 __init__.py files — The Room Labels

📄 src/__init__.py, src/scraper/__init__.py, etc.
Empty files that tell Python "this folder is a package (a group of related code)."
Like putting a "RECEPTION →" sign on a door. Without it, Python doesn't know this folder contains code it can use.

How to Run Phase 0

Open a terminal (Command Prompt or PowerShell) and type these commands one at a time:

Step 1 — Install the tools

pip install -r requirements.txt

This reads the shopping list and downloads everything.

Step 2 — Install the browser

python -m playwright install chromium

This downloads Chromium (a browser like Chrome) that the robot will use.

Step 3 — Create the database

python -c "from src.storage.database import init_db; init_db()"

This creates the data/apix.db file with empty tables, ready to receive data.

Step 4 — Verify everything works

python -c "from src.models.schemas import FlightRecord; print('All good!')"

If you see "All good!" — Phase 0 is complete.

Self-Check Quiz

Try answering these to see if you understood:

Q1: What does the .env file store?

Settings and secrets — things like where the browser is installed, how fast to make requests, and the log level. It's kept private and not shared via GitHub.

Q2: Why do we need requirements.txt?

Python doesn't come with Pandas, Playwright, etc. pre-installed. requirements.txt tells Python exactly which extra tools to download so anyone can set up the project identically.

Q3: What is a database in simple terms?

A structured file that stores data in tables (like Excel sheets). Our database (SQLite) has 5 tables: raw_flights, cleaned_flights, and 3 index tables.

Q4: Why do we have __init__.py files that are empty?

They tell Python that the folder is a "package" — a group of related code files that can import from each other. Without them, Python wouldn't recognize the folder structure.

Q5: What's the difference between raw_flights and cleaned_flights tables?

raw_flights has messy, unprocessed data straight from Google Flights (may have duplicates, outliers, missing values). cleaned_flights has the same data after Pandas has cleaned it — removed errors, filled blanks, and flagged suspicious prices.
